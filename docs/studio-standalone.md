# 独立的 Synon Studio 应用与无人值守的 Beluga 集群（设计稿）

状态：**设计稿，未实施，未审计**。P1 里 Studio 是「客户 Web + 中台 + 编在 Beluga 里的一块界面」，批准开工要有人坐在
Beluga 前面点。本文把它改成：**人只在 Studio 里，Beluga 无人值守地执行。**

**已定的前提（2026-11-18）**：

- **客户是 Studio 唯一的使用者，自己做全部决定**：提需求、确认理解、批准开工、维护环境与密钥、验收、批准上线。
  Studio 里没有「工作室主人」这个角色，Beluga 的界面里也不出现这些决定。（同日较早的一版写的是「主人也用 Studio
  应用，有收件箱和批准卡」，已作废。）
- **Beluga 节点无人值守。** 没有人看它的窗口、铃铛或手机伴侣。任务从 Studio 发到 Beluga，Beluga 执行、检查、回报。
- **交付自动。** 检查通过、预览生成后直接给客户看；客户点「通过」就是验收。
- 集群里的节点都是同一个人（搭这套环境的人）的机器，用同一个人的登录与订阅。
- **客户的桌面应用做 Tauri 壳，并把本机能力用上**（§2.2）；手机 App 与 Web 同时做。界面见
  [`studio-ui.md`](studio-ui.md)，代码交付见 [`studio-forges.md`](studio-forges.md)，环境与密钥见
  [`studio-env.md`](studio-env.md)。

先读：[`studio.md`](studio.md)（P1）、[`studio-loop.md`](studio-loop.md)（需求单与交付）、
[`studio-hub.md`](studio-hub.md)、[`studio-daemon.md`](studio-daemon.md)、[`machines.md`](machines.md)。

## 0. 结论摘要

- **一个人用的界面，一组没人看的机器。** 客户用 Studio；Beluga 节点只执行。两者只经中台和节点上的连接器相连，
  Studio 应用永远不直接连节点。
- **批准经过中台，所以要签名。** P1 的批准在 Beluga 本机点，中台够不着。现在批准从客户的设备发出、经中台到节点，
  中台就站在了路上：批准开工、批准上线、写入密钥、通过交付，都由**客户设备上的密钥签名**，节点验签后才执行。中台
  被攻破也伪造不了这些动作，也读不到密钥。
- **信任从邀请开始，不经中台。** 节点生成邀请链接，链接里带一个一次性的密钥和节点公钥的指纹，放在 `#` 后面，由
  搭环境的人亲手交给客户。客户的设备用它向节点登记自己的公钥。中台只转发，拿不到这个密钥。
- **无人值守就要自己兜底。** 没有人在 Beluga 前面处理异常：放置、换节点、合并、生成预览都自动；自动不了的（节点
  全离线、agent 掉登录、用量到顶）在客户那里显示「等待」和原因，并给搭环境的人发一封邮件。
- **集群的单位是计划，不是任务。** 一个需求单 / 计划归一个节点；中台只做「放到哪个节点」，依据是节点自己报的
  「能不能接、还有多少空位」。

## 1. 谁，用什么

| 谁 | 用什么 | 做什么 |
|---|---|---|
| **客户** | Studio 应用（桌面、手机、Web） | 全部决定：提需求与反馈、回答问题、确认理解、批准开工、维护环境与密钥、验收、批准上线 |
| **节点** | 一台跑着 Beluga daemon 的机器，无人值守 | 分析、规划、开发、检查、合并、生成预览、上线；发布净化后的视图；只执行签过名或在白名单里的动作 |
| **搭环境的人** | 节点上的 `beluga studio` CLI，一次性 | 连节点、共享项目、发邀请、设上限；之后只在收到「需要人」的邮件时出现 |

```
Studio 桌面 / 手机 / Web ──► 中台 ◄── 出站连接 ── 节点 A
          客户                   │  ◄── 出站连接 ── 节点 B
                                 └─ ◄── 出站连接 ── 节点 C（服务器，无窗口）
```

「搭环境的人」不是 Studio 里的角色，没有界面。可以就是客户本人（自己有几台机器、自己用），也可以是替客户搭好就走
的人。

## 2. Studio 应用

### 2.1 三个目标，一套界面代码

| 目标 | 做法 | 现状 |
|---|---|---|
| 桌面（macOS 先，之后 Windows） | 新 `packages/studio-desktop`：Tauri 2 壳装 `packages/studio-app` 的 Web 构建，加本机能力 | 新 |
| iOS / Android | 同一个 Expo 工程出原生包；推送走 APNs / FCM | P2 已列入 |
| Web | Expo 导出静态站，中台同源托管 | P1 已有（开发代理） |

三个目标都**不内嵌 daemon**。界面代码只有一份；本机能力经一层 `lib/native.ts`（桌面走 Tauri 命令，手机走 Expo
模块，Web 给降级实现），页面不直接碰平台。

### 2.2 桌面壳用上的本机能力

Beluga 的 Mac 应用已经在用这些 Tauri 插件（notification、deep-link、dialog、opener、window-state、
clipboard-manager、single-instance、updater、global-shortcut、tray-icon），Studio 的壳照搬同一套，不引入新技术。

| 能力 | 做什么 | Web 上的降级 |
|---|---|---|
| 钥匙串 | 设备密钥（§5）存系统钥匙串，不可导出 | WebCrypto 不可导出密钥，存 IndexedDB |
| 系统通知 + 菜单栏图标 | 「等你」的事立刻通知；菜单栏图标带待办数，点开是待办列表 | Web Push |
| 深链 `synon://` | 邀请链接、通知、邮件直接打开到那条需求 | 普通 `https` 链接 |
| 全局快捷键 | 任何时候呼出「提需求」小窗 | 无 |
| 截屏并标注 | 提反馈时截当前屏幕、圈出问题，作为附件 | 上传图片 |
| 拖入文件与文件夹 | 需求文档、设计稿、表格拖进输入框当附件（只读，确认清单后才上传，见 `studio-env.md` §9） | 文件选择框 |
| 本机预览 | 交付的 Web 构建在内置窗口里打开；安装包下载后用系统打开 | 新标签页 |
| 本机 git | 交付的代码「克隆到本机」「在编辑器里打开」；凭证进钥匙串（见 `studio-forges.md`） | 只显示仓库地址 |
| 离线草稿与自动更新 | 没网时需求先存本机，上线后发；应用自己更新 | 浏览器本地存储 |

一条边界：**本机文件只读、只在客户点了之后上传**。壳不扫描磁盘，不给 agent 任何本机权限；agent 在节点上跑。

Web 上的设备密钥较弱（清站点数据即丢、挡不住恶意扩展），所以设置里列出每台设备并可逐个移除；批准开工与上线建议在
桌面或手机上做，Web 上做时提示一句。

## 3. 从「有人值守」到「无人值守」改了什么

P1 和 `studio-loop.md` 里有几处默认有人坐在 Beluga 前面。逐条改成：

| 原来谁做 | 事情 | 现在 |
|---|---|---|
| 你，在 Beluga 铃铛里 | 批准开工 | **客户**在 Studio 里，签名 |
| 你，在 Beluga 铃铛里 | 确认交付 | **自动**：最后一个里程碑检查通过、预览生成后，交付 Gate 自己通过 |
| 你，在 Beluga 计划页 | 加预览 | **自动**：节点部署到测试环境，把地址作为预览（`studio-env.md` §6） |
| 你 | 合并 | **自动**：检查通过后由节点合并（`studio-forges.md` §3.2） |
| 你 | 批准计划的改动（「还不行」后的补丁） | **客户**在 Studio 里，签名 |
| 你 | 兜底的需求单卡（没人分析、轮数超限） | 客户看到「等待」与原因；搭环境的人收到邮件（§4.6） |
| 你，在中台管理页 | 邀请客户、项目映射 | 搭环境的人在节点上用 CLI，一次性（§5.1） |
| 你，在 Beluga | 正式环境上线、密钥 | **客户**在 Studio 里，签名（`studio-env.md`） |

Beluga 的 Mac 应用里保留已有的「连接」与「状态」，给搭环境的人排查用；Studio 的决定不在 Beluga 里出卡。P1 的
`studio-start` 卡在本设计下不再升起（待定 4）。

## 4. 集群

### 4.1 为什么每个节点各自连中台

Beluga 的「Your Computers」里，工作跑在哪台机器，状态就只在那台机器的 daemon 里（`machines.md`）。连接器要读计划、
发视图、执行动作，所以它必须在**计划所在的那台机器**上。因此每台都带连接器、各自出站连中台。

`studio.link` / `studio.setProject` 在跨机器调用里是 `refuse`（`src/machines/coverage.ts`），所以每台节点要在它自己
上面连一次：`beluga studio link <code>` 与 `beluga studio share`。

### 4.2 要改的一条规则：节点池

中台已经允许一个工作室登记多台 daemon（`daemons` 表按 `studio_id`）。挡住集群的只有一条：**一个 Studio 项目只绑
一台 daemon**（`projects.daemon_id`，`studio-daemon.md` §2.3）。改成：

```sql
project_nodes (project_id, daemon_id, daemon_project_id, enabled,
               PRIMARY KEY (project_id, daemon_id), UNIQUE (daemon_id, daemon_project_id))
placements    (project_id, ref /* requestRef 或 planRef */, daemon_id, placed_at, PRIMARY KEY (project_id, ref))
```

「一个 daemon 的一个本地项目只映射一个 Studio 项目」保留。

### 4.3 放置（全自动）

- **何时放**：`request.create` 入队时（`studio-loop.md` §2）。
- **节点报什么**：`hello` 之后每次变化上报 `load{ready, why?, room}`。`ready` 与 `why` 用 Beluga 的 Best Available
  已经在看的那些条件来算（`machines.md`「Run New Work On」）：agent 已登录、没到用量上限、项目在这台机器上、
  内存磁盘够；`room` 是还能同时接几个。只是一个布尔、一个原因码、一个数，没有模型名与路径。
- **放哪**：池里 `enabled`、在线、已 `synced`、`ready` 的节点中取 `room` 最大的；并列取上次接活最早的。没有人指定。
- **没有可用节点**：需求单排队，客户看到「等待：<原因>」（例如「执行机器用量已满，16:00 恢复」）。
- **粘住**：需求单变成计划后继承同一个节点；下一轮（`plan.follows`）也优先同节点，因为代码在那。
- 节点满了可以回 `busy`，中台换下一个。

### 4.4 同一个计划，换了节点还认得

**`refKey` 归工作室，不归单台 daemon**。第一台节点连上时生成；之后的节点在连接时从已有节点取得（经
「Your Computers」的端到端通道，不经中台；中台始终拿不到 `refKey`）。于是同一个需求单 / 计划在哪台节点上，ref
都一样。

### 4.5 节点掉线

| 这件活处于 | 做法 |
|---|---|
| 需求单还在分析，或计划还没开工 | 等 15 分钟；还没回来就**自动换一台**：中台把需求单原文重发给新节点，旧节点回来后收到 `withdrawn` 把自己那份关掉 |
| 计划已开工 | **不自动搬**。代码在那台机器上，客户看到「等待：执行机器离线」，等它回来；超过 2 小时发邮件给搭环境的人 |

没开工的活自动换节点，是因为没有人会来手动换；开工后的活不换，是因为两台节点对同一份代码各改一份比多等一会儿更糟。

### 4.6 需要人的时候

无人值守也会遇到机器自己解决不了的事。中台按下表处理，**客户那边永远只看到「等待」和一句原因**，不写失败，不让
客户去修他修不了的东西：

| 情况 | 客户看到 | 搭环境的人 |
|---|---|---|
| 所有节点都离线 | 等待：执行机器离线 | 15 分钟后一封邮件 |
| agent 掉了登录 | 等待：执行机器需要重新登录 | 一封邮件 |
| 用量到顶 | 等待：用量已满，几点恢复 | 不发（会自己恢复） |
| 分析或开发反复失败（轮数超限） | 等待：这条需求需要人看一下 | 一封邮件，带需求单标题 |

邮件一天每类最多一封。邮件地址是搭环境时 `beluga studio link` 填的那个，中台本来就会发登录邮件。

### 4.7 新项目：客户自己新增，放在哪

客户可以在 Studio 里**新增项目**（`studio-ui.md` §2.5），两种开始：**空项目**，或**从仓库导入**（GitHub、cnb.cool，用登录
选仓库）。数量**不设上限**。以前一个 Studio 项目只是映射到节点上已有的本地项目，由搭环境的人 `beluga studio share`；
现在新增项目是客户的日常操作，所以建项目也要自动：

1. 应用调中台 `POST /v1/app/projects {name, platforms[], source}`，会话鉴权。`source` 是 `{kind:'empty'}`，或
   `{kind:'import', provider:'github'|'cnb', repoUrl, branch?, sealedToken}`。**空项目不签名**（不花钱、能归档）；
   **导入要设备签名**，因为它把一个能读客户代码的令牌交给节点（§5.3）。令牌由应用用节点的公钥**封好**，中台只转发密文。
2. 中台建 `projects` 一行，然后按 §4.3 选节点（在线、已 `synced`、`ready`、`room` 最大）；没有可用节点就把项目记为
   `preparing`，客户看到「等待：正在准备」，节点回来后补做。
3. 中台给节点发 `project.create{projectRef, name, platforms, source}`（导入时带签名帧，原样转发）。节点：
   - 空项目：在它配置的项目根目录下建一个空的本地项目（目录、`git init`、项目登记）。
   - 导入：验签（信任名单）、解封令牌，用 git 凭证助手 `clone`（令牌不写进地址、不进日志），令牌按项目存进节点的
     密钥库（`studio-env.md`），之后「推到我的仓库」可以直接用，客户不用再填一遍。
   然后自动 `share` 给这个工作室，回 `project.ready{projectRef, daemonProjectId}`；失败回 `project.refused`。
4. 中台写 `project_nodes`（§4.2）。之后这个项目的需求都按 §4.3 放置。
5. 客户端轮询或收推送，项目出现在列表里，能提需求。空项目应在几秒内；导入看仓库大小，进度写在项目行上；超过 10 分钟
   仍是 `preparing` 就按 §4.6 处理。

导入后**代码交付默认仍是「只给预览」**，不自动往客户仓库里推；要推，在设置里选「推到我的仓库」（用同一个令牌，
但 CNB 的登录令牌只有 8 小时，见 `studio-forges.md` §3.5）。克隆在节点上做，Studio 应用里看不到源代码。

## 5. 身份、邀请与签名

### 5.1 搭环境：一次性，在节点上

1. `beluga studio link <code>`、`beluga studio share`：和 P1 一样。
2. `beluga studio invite <客户邮箱>`：节点生成一条邀请链接
   `https://<hub>/join/<inviteId>#k=<一次性密钥>&n=<节点公钥指纹>`。`#` 后面的部分浏览器不发给服务器，中台看不到。
3. 搭环境的人把链接**亲手**交给客户（微信、当面）。不经中台的邮件，因为那样中台就看见了。
4. 链接 7 天有效，用一次即废。

### 5.2 客户的设备

- **账号**：邮箱 + 魔法链接登录（同 P1）。会话由中台管，只管「能看、能发白名单动作」。
- **设备密钥**：Studio 应用第一次打开邀请链接时在本机生成一对密钥（Ed25519 签名 + X25519 封装，存放见 §2.2）。
- **登记**：设备发 `device.enroll{pubkey, mac}`，`mac = HMAC(一次性密钥, pubkey)`。节点核对 `mac`，记下这把公钥；
  同时设备核对节点回的公钥与链接里的指纹一致。从此双方互相认得，中台在中间换不了钥。
- **加第二台设备**：在已登记的设备上点「加一台设备」，出一个二维码（里面是新的一次性密钥），新设备扫码后同样登记。
  手机扫桌面最常见。
- **移除设备**：在任意一台已登记的设备上做，签名。全部设备都丢了，只能让搭环境的人再发一条邀请。
- 节点的信任名单（`studio-trust.json`，0600）经「Your settings follow you」同步到同一个人的其他节点。

### 5.3 签什么，不签什么

| 签名（节点验签后才执行） | 不签（会话鉴权 + 白名单就够） |
|---|---|
| 批准开工、批准计划的改动（`gate.answer`，绑定 `draftRev`） | 提需求、说话、回答问题 |
| 确认理解（`request.confirm`，绑定 `rev`）：它决定了开工的范围 | 上传设计稿、撤回需求 |
| 通过交付（`delivery.accept`）：之后会推代码、打标签 | 还不行（只是把原因交回去分析） |
| 批准上线（`release.approve`） | |
| 写入、更换、删除密钥（`env.setSecret` / `delSecret`，值封给节点） | |
| 改环境与代码交付设置（`env.put`、`delivery.config`） | |
| 加、移除设备 | |

整帧签名：`{kind, payload, rev?, at, deviceKey}`。`at` 严格递增，防重放。节点在执行前检查：公钥在信任名单里、签名
对、`rev` 是当前的。

**最坏情况**：中台被攻破后，能读到客户的需求与对话（P1 就能），能扣下动作不发，但**不能**替客户批准开工、上线，
不能读或改密钥，不能改代码推到哪。条款里写明。

## 6. 客户看到什么

客户视图仍是 P1 的白名单视图（净化过，没有路径、任务 KEY、分支、模型名、代码）。设置里多三样，都是只读或签名写：

| 设置页 | 内容 | 来源 |
|---|---|---|
| 执行机器 | 几台、在不在线、能不能接、正在做哪几条需求 | 节点的 `load` 与 `placements`，不含机器路径与模型 |
| 环境与密钥 | 环境、变量、密钥的名字与更新时间 | `studio-env.md` |
| 代码交付 | 交付方式、仓库、最近一次交付 | `studio-forges.md` |

源代码、diff、终端：客户在 Studio 里看不到。选了「给仓库」的客户去托管平台看。

## 7. 上限：无人值守的刹车

客户批准开工就会花真钱（agent 用量）。没有人在 Beluga 前面盯着，所以上限由搭环境的人在节点上设好：

- 每个项目同时在做的需求不超过 N 条（默认 2）。
- 每个月的用量上限；到了以后新开工排队，客户看到「本月用量已满」。
- 单条需求的最长运行时间（默认 8 小时）；超了暂停，按 §4.6「需要人」处理。

`beluga studio limits` 设置，只在节点上，不在 Studio 里（客户改不了自己的刹车）。

## 8. 连接器：Beluga 这一侧

- 连接器仍是 daemon 进程内的模块（`src/studio/`）。客户回合的工具边界、净化视图、「只有签过名的 Gate 能批准」必须在
  核心里强制，做成外挂守不住。
- **每个节点都跑带连接器的 Beluga 构建**（本仓库的 daemon）。
- 对 Beluga 核心的要求保持「只留钩子」。新增的钩子：算 `load` 时复用 Best Available 的判断（只读）；计划 Move To
  落地后通知连接器重新发布；Autopilot 在交付方式为自动时不停在最后的交付 Gate。
- 连接器新增：验签与信任名单、邀请（`beluga studio invite`）、`refKey` 的取得、`busy` / `withdrawn` 应答、上限、
  「需要人」的原因码。

## 9. 协议改动

都在 `STUDIO_PROTO.major = 1` 内做加法：

- 应用 → 中台 → 节点：签名动作（§5.3 左列）原样转发，中台不解开；`device.enroll`。
- 节点 → 中台：`load{ready, why?, room}`；回执码加 `busy`；`needsHuman{why, ref?}`（中台据此发邮件）；设置视图
  （执行机器、环境名字、代码交付）。
- 中台 → 节点：`withdrawn{ref}`；`project.create{projectRef, name, platforms, source}`
  （导入时附签名帧与封好的令牌，中台不解开）。节点 → 中台：`project.ready{projectRef, daemonProjectId}`、
  `project.refused{projectRef, why}`（`exists` / `bad-name` / `clone-failed` / `bad-token`）、导入进度
  `project.progress{projectRef, percent?}`。应用 → 中台：`POST /v1/app/projects`（不限数量）。
- 旧节点（不报 `load`、不会验签）不能接新协议的项目：中台在绑定时就拒绝，提示升级。

## 10. 与 P1 的差异

| 项 | P1 | 本设计 | 理由 |
|---|---|---|---|
| 谁在用 | 客户在 Web，你在 Beluga | 只有客户，在 Studio | Beluga 无人值守 |
| 谁批准开工 | 你，在 Beluga 本机 | 客户，设备签名 | 没有人在 Beluga 前面 |
| 交付 | 无（P2 设计是你确认） | 自动 | 同上 |
| 批准的信任 | 只在本机，不经中台 | 经中台转发，签名，节点验签 | 中台站在了路上 |
| 信任从哪来 | 不需要 | 节点出的邀请，`#` 后的一次性密钥 | 中台看不到 |
| 项目 ↔ daemon | 一对一 | 节点池，自动放置，没开工的掉线自动换 | 集群、无人值守 |
| `refKey` | 每台 daemon 一把 | 每个工作室一把，只在你的机器之间传 | 计划搬家后 ref 不变 |
| 异常 | 你在 Beluga 里看到 | 客户看到「等待」，搭环境的人收邮件 | 无人值守 |
