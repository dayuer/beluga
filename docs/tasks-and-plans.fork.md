# Tasks and plans: what this fork adds

This fork's part of [tasks-and-plans.md](tasks-and-plans.md), kept here so that file stays upstream's (docs/fork.md, min-conflict). Each paragraph sits in the same section there ("Plans"); a paragraph here with the same bold start as one there replaces it.

- **What only you can do, asked mid-task.** A task's agent (or a milestone's) that needs something only you can do or decide (a step on your server or an account, a secret, a choice) asks with AskUserQuestion (`ASK_YOU` in `prompt.ts`): a card in its chat, on your phone too, and your answer goes back into the same turn. Written out with the turn ended, it read as stopping: woken, then *stopped again* with only Resume, again and again (TRC-151 asked for a `.env` that way). If one still stops like that, what it said last is kept on its watch (`TaskWatch.said`) and is what the plan's next step, its feed, the notification and the phone's card show: *KEY waits for you · It last said: “…” If it asks for something, do it (or answer in its chat), then Resume it.* (What it said last isn't always a request, so it's not called one.)
- **A checker per milestone.** A milestone's check isn't the head agent's: it gets a **checker of its own**, a fresh agent in a conversation made for it in the project (`PilotDeps.checkerChat`, recorded as `runs[id].checker`, folded into the plan like its home and worktrees). It didn't write the code nor plan it, and it has only `plan_get` and `plan_gate` (for its own milestone). So the plan's conversation stays free for you while it checks, and milestones that finish together are checked side by side. Its verdict reaches the head conversation as one line; a failed one also goes to the head agent with the notes, to add the fix tasks (applied at once on Autopilot). A later round goes to the same checker, which remembers what failed. Passing archives it (what it said is kept). With no conversation to make, the head agent checks as before. **Which agent checks:** the plan's ⋯ › Plan Settings… › Audit (`plans.setCheckAgent`, kept as the plan's `checkAgent`), else the agent for its work (`checkerAgentOf`). So cheap models can do the work and a stronger one checks it, on Autopilot too; Verify the Plan's reviewer runs on the same agent. **The plan's own conversation** runs on the agent for its work: a plan made with one opens its conversation on it, and Agent for Its Work ▸ (`plans.setWorkAgent`) moves the conversation too, as its own picker would (another runtime gets the recent conversation with the next message). Picking the same agent again brings back a conversation that drifted from it. With an agent for its architecture (below), the plan's conversation runs on that one instead: cutting the plan into milestones is design work too (`homeAgentOf`).
- **Who does what, by tier.** New Plan › More options has a pop-up per role, each starting on its tier's model (`planRoleDefaults` in `shared/auto-route.ts`, the first of the list that runs here, auto route on or not): **Architecture** and **Hard fixes** on the strong list (Opus), **Coding** on the cheap one (with auto route on, each task routed as it starts; off, the cheap list's first), **Audit** on the `review` list in between (Sonnet; Settings › Auto Route › Plan Audits). A plan nobody picked a checker for is checked by the review list's first too (`autoChecker`). Any role can be any agent instead, then or later in the plan's ⋯ › Plan Settings…
- **What's hard goes to the fix agent.** The plan's ⋯ › Plan Settings… › Hard fixes (`plans.setFixAgent`, kept as `fixAgent`; none: auto route's strongest, `autoFixer`; auto route off too: whoever is at it, as before) takes over three things, each by a quiet switch of the conversation (`PilotDeps.switchAgent`: the recent conversation comes along): a milestone's **fix tasks after a failed check** (handed to its worktree, the worktree moves to the fix agent; a fresh start opens on it); a **conflict** (combining a task's bases, merging a milestone or main into the plan's branch: the plan's conversation moves to the fix agent while it fixes it, and back once the conflict is gone); and a **task that stopped twice** (the watchdog, instead of leaving it to you on the second stall, moves its conversation to the fix agent and wakes it once more, `TaskWatch.escalated`; stopping a third time, it waits for you). Each conversation is switched once; the plan's activity says so. Two conflicts at once keep the plan's conversation on the fix agent until both are gone, and a conversation already on the fix agent (say, from before the daemon restarted) isn't handed over again and still comes back once its conflict is gone.
- **An architect per milestone** (optional). With the plan's ⋯ › Plan Settings… › Architecture set (`plans.setArchAgent`, kept as the plan's `archAgent`; none, the default, is no architect step), a milestone's work doesn't start straight away: first an **architect of its own**, a fresh agent on that agent in a conversation made for it (`PilotDeps.architectChat`, titled *Design: …*, recorded as `runs[id].architect`, folded into the plan like its checker), reads the plan and the code and writes the milestone's technical design: the modules and files to change, interfaces and data shapes, how its tasks fit together, risks. It has only `plan_get` and `plan_design`, changes no code and commits nothing. `plan_design` keeps the design on the milestone (`runs[id].design`) and its work starts on the next look: the milestone's agent gets it in its prompt and brief and follows it (saying in its handoff where and why it departed), and its checker checks the work against it. The architect doesn't count against the plan's limit of milestones at once, and is archived when the milestone passes. It never stalls a plan: a turn that ends without a design is asked once more, and if it ends without one again the plan says so and the work starts without a design. Step-by-step milestones are designed too, but your Start doesn't wait for it; a milestone already at work when you set it keeps going. The design shows in the milestone's details on the Mac and on the phone.
- **Who did it.** A milestone's details on the Mac (and its card on the phone's plan page, 1.55) say who really did each part, read from where each ran rather than from the settings: **Architecture** is the model of its *Design: …* conversation, **Coding** the model its worktree started on, **Audit** the model of its *Check: …* conversation, and **Hard fixes** the fix agent with each handoff (the fix tasks, a task that stopped twice, a stuck conversation), from the plan's activity (`src/fork/plans/roles.ts`). A part not begun says *Not started yet* with the model that will do it; one the plan doesn't set says *Not set*. When what ran isn't what the plan sets now, the line is marked with why: picked with Start with…, the task's own agent, a failed check (the fix agent took over), nothing set runs here (your default agent), or the plan's setting changed after it started. Each task card shows the model of the worktree at work on it (before it starts, in the list, who will). A milestone's worktree starts on the agent you started it with, else its first task's own agent, else the fix agent (after a failed check), else the plan's, else auto route's pick for that task (Coding left to auto route: an everyday model, or the strong list for a hard task), else your default (`workAgentFor`). It's kept on the milestone as it started (`MilestoneAgent.agent`, `via`).
- **Task titles don't pick models.** A task's role is set only by the plan's settings. Words like 【设计】 or 【审计】 in a task's title don't send it to the architect or the checker: all of a milestone's tasks are done in its one worktree, by the Coding model (or the task's own agent, if it has one). The architect writes the milestone's design before that work starts, the checker checks the milestone once its tasks are done, and the fix agent takes over only what's hard.
